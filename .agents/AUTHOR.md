## 一、先开自己的 worktree（不这么做会被钩子挡住）

主目录 `C:\Users\lintian\pptx-finder` 是这个项目的最终版本，**在那里提交会被 pre-commit 直接拒绝**。

```bash
git worktree add C:/AIWork/<日期>-<任务简称>-<你的席位> -b <分支名> master
cd C:/AIWork/<同上>
uv sync                     # 在 worktree 里建它自己的 .venv
```

- 分支名用 `feat/` `fix/` `chore/` 开头 + 一句能看懂在干嘛的短语
- `uv sync` 大约 **2 分钟**（2026-09-08 实测 1 分 57 秒），别以为它卡住了。
  它是从 uv 全局缓存（`C:/Users/lintian/AppData/Local/uv/cache`）**硬链接**过来的
  （实测 .venv 里的 DLL 硬链接数=2），同一个盘符，几乎不占额外磁盘，也碰不到主目录。
  装完先跑一个快文件确认能自测：`uv run pytest -q tests/test_parser.py`（约 2 秒）
- 别去动主目录里别人的未提交改动

### ⚠ 绝对不要把主目录的 `.venv` 借给 worktree

`.venv/Lib/site-packages/pptx_finder.pth` 里写死的是一行绝对路径：

```
C:\Users\lintian\pptx-finder\src
```

`tests/conftest.py` 不往 `sys.path` 里塞任何东西，**导入完全靠这个 .pth**。
所以只要你把 `VIRTUAL_ENV` / `UV_PROJECT_ENVIRONMENT` 指向主目录的 `.venv`，
在 worktree 里跑出来的测试**测的是主目录的代码**——全绿也证明不了你改的东西是对的。
这类假证据不会报错，只会让你和合并位一起判错。**每个 worktree 必须有自己的 `.venv`。**

## 四、自己跑一遍（这是给自己看的，不叫审核）

```bash
uv run pytest -q                      # 全量：1718 条 / 14 分 36 秒
uv run pytest -q -m "not slow"        # 快档：1704 条 / 约 10 分 45 秒
uv run pytest -q tests/test_xxx.py    # 迭代时就跑你改的那几个文件，单文件通常几秒到十几秒
```

（`slow` 那 14 条是 100 万文件清点、10 万目录树这类压力测试，跑 3 分 50 秒；
真正会起 PowerPoint COM 的只有 `test_render_real_page` 一条。）

**这套测试很慢，别拿全量当迭代手段**：改代码的循环里只跑相关文件，
**交付前跑一次全量**。合并位的闸门跑的就是全量，你报的结果对不上会被当场发现。

### 跑测试前先看一眼 PowerPoint

带 `slow` 标记的 14 条会**真的起 PowerPoint COM**。跑之前确认你自己没开着 PPT 窗口；
写渲染相关的脚本时只关自己创建或打开的对象，**不要碰别人已经开着的演示文稿**。

测试已经把数据目录改到临时目录（`conftest.py` 设 `PPTX_FINDER_DATA_DIR`），
不会污染真实索引库，这一点不用你操心。

### 改 UI 就真看一眼

```bash
uv run python -m pptx_finder
```

**不要用 `QT_QPA_PLATFORM=offscreen` 去量字号、行距、排版常量。**
离屏不加载系统字体，同一张图离屏算出 8.5~9.7pt、真实平台 11.6pt。
这类常量必须在真实平台上量。

## 五、不要碰版本号

`pyproject.toml` 和 `src/pptx_finder/__init__.py` 里的版本号，**分支一行都不要改**。
合并脚本会在合并那一刻把两处一起抬。

原因：那两行是所有并行分支都要改的同两行，而「我是第几个合进去的」这个信息只有合并那一刻
才存在。分支自己抬，两个群聊同时开工必然撞车。要改主/次版本号是人的决定，告诉维护者。

## 六、这个项目的红线（越过就是事故）

- **版本库 / 留底 / 对象池**：全应用最不能出错的地方。对象文件名永远是**未压缩内容**的
  xxh64，`.z` 只是存放形态；manifest / 去重 / GC / 体检一律按哈希对账，不认文件名形态。
  存量零件一个都不动。压完必须解压回来逐字节比对才允许落盘。
  留底自检不过会**静默退成 `mode=full`**，测试钉着这条，别把它放松。
- **不要"优化"整库建索引的速度**：低优先级、最多 2 worker、用户一交互就暂停，是设计如此。
- **不要以"省磁盘"为由关掉 Everything 全文件索引**（+1.19 GB）。用户明确拍过板：
  藏在设置里的开关等于没有能力。
- **不发布、不上传 ECS**：打包发布和 `.selftest/release.py`（要 `ECS_PWD`）一律等用户点头，
  工作位不碰。

## 七、怎么向维护者说话

维护者不看代码。他要判断的是方向对不对、值不值得、有没有坑，不是你改了哪个函数。
他能看到的只有下面这几个标签里的内容——**你不写，他就什么都看不到**。

### 开工前

```
PLAN: 我打算怎么做
准备动哪几块、为什么这么切、有什么取舍或不确定。
```

### 实现中：每到一个可解释的阶段就写一条

```
UPDATE: 刚完成什么，现在在做什么，或者被什么挡住
```

判据是「有没有新信息」，不是「过了多久」。不要为了写 UPDATE 而额外调用模型。

### 需要拍板时

```
ASK: 需要你决定的问题
两个选项各自的代价，以及你的推荐。
```

### 交付时：四行协议 + 一段说明

群里最后必须原样输出这四行（机器要解析，标签用英文冒号，各占一行、不要跨行）：

```
PROGRESS: 一句话说清你干了什么，别写文件名和函数名
VERIFIED: 实际跑了什么、什么结果，写数字
RISK: 有什么要注意的；确实没有就写「无」
REPORT: HTML 报告的绝对路径；没有就写「无」
```

**最终交接前不要提前输出这四行**；`UPDATE` 不表示完成。四行之后再写一段：

```
NOTES: 给维护者的说明
做了什么、为什么这么做、什么明明可以做却没做、怎么验证的。
```

**别贴代码、别列文件清单。**

## 八、交给合并位

```bash
git push -u origin <你的分支>
```

推主干会被 pre-push 挡住，这是故意的——主干只有合并脚本一个入口。

推完在群里说一句：「分支 `<名字>` 可以审了」，然后停下等合并位。

## 九、被打回时

合并位会给 `BLOCKERS`。**只修 BLOCKERS 里列的东西**，别顺手改别的——
那会让下一轮审查失去对照。改完再推同一个分支，重新说一句可以审了。
