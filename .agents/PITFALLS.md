# 这个项目已经用实测否掉的路（走一遍就是白花一晚上）

> 知识文件，不讲流程。`AUTHOR.md` / `MERGER.md` 引用它，不抄它。
> 每条都是本机实测得出的，日期是得出结论的时间。

## 环境

- **`QT_QPA_PLATFORM=offscreen` 不加载系统字体。** 调字号/行距/排版常量必须在真实平台上量：
  同一张图离屏算出 8.5~9.7pt、真实平台 11.6pt。（2026-08-27）
- **worktree 必须有自己的 `.venv`。** `.venv/Lib/site-packages/pptx_finder.pth` 里写死
  `C:\Users\lintian\pptx-finder\src`，`tests/conftest.py` 不改 `sys.path`——
  借用主目录的 venv 等于在测主目录的代码，全绿也不证明什么。

## 内存 / CPU：三个假设已被 A/B 否掉，别再走一遍（2026-08-28）

核心引擎（索引+搜索）只有 60 MB；主窗口 215 MB 工作集 / 134 MB 私有。被否掉的：

1. **控件数**——1 页 183 控件 193 MB vs 4 页 726 控件 205 MB，4 倍控件只差 12 MB
2. **样式表**——整张去掉仍 215.3 MB
3. **字体回退链**——全部去掉仍 215.5 MB

字体那条在**合成测试**里显示能省 82 MB，放到真实窗口三次都复现不出来，改动已回退。
**教训：合成测试的结论不一定迁移，必须在真实对象上复验。**

CPU 也没有优化空间：托盘空闲 0.02%（20 核 30 秒采样），索引 17 ms/文件，搜索 5 次 0.01 秒。
**整库建索引慢是设计如此**（低优先级、最多 2 worker、用户一交互就暂停），不是缺陷。

## 存储：方向不全是"省"（2026-08-28）

- 已修：索引库空闲页 + WAL，164 MB → 17 MB。根因是 VACUUM 的两个门槛写成了"与"，
  132 MB 的库永远够不到"空闲 256 MB"，一次都没跑过。
- 已修：预览缓存上限 2 GB → 512 MB。
- **净增且不许改回去**：Everything 全文件搜索改为常开，索引库 +1.19 GB。
  用户明确拍板要这个——藏在设置里的开关等于没有能力。

## 版本库压缩：三条铁律 + 一个坑（2026-08-28）

真实版本库盘点（不必重测）：对象池 48,775 个 / 3,175 MB，4,101 份 manifest。
`.xml`/`.rels` 文本零件 889.9 MB（字节占 28%、个数占 77%），媒体 2,090.5 MB（65.8%）。
文本零件实压到 11% → 全部换血可省 788 MB。

**不可动摇的三条：**

1. 对象文件名永远是**未压缩内容**的 xxh64，`.z` 只是存放形态；
   manifest / 去重 / GC 引用集 / 深度体检全部按哈希对账，**不认文件名形态**。
2. 存量零件一个不动，读取按 `<hash>` → `<hash>.z` → 旧的每文档池解析。
   所以 788 MB 是逐步兑现的，不是升级当天到账。
3. 压完必须解压回来**逐字节比对**才允许落盘，对不上就退回存原始件。

**坑：先写原始件再写压缩件会吃掉全部收益。** 文本零件占对象个数的 77%，双写等于把落盘
次数翻倍——12 份真稿实测 12.6 s → 16.4 s。改成小 part 走内存路径、只落一次盘之后
变成 13.7 s → 9.2 s（比压缩前还快）。**动这条路径先量「每个零件落几次盘」。**

**静默退化要盯住**：留底会先重组做保真自检，自检不过就退成 `mode=full` 整份拷贝——
解压路径出问题时**不报错**，只是版本库不降反涨。已有测试钉住「留底不许退成 mode=full」。

## 图片转可编辑文字：怎么测（2026-08-27）

**没有标准答案时测正确率**：把转出的 PPTX 用 PowerPoint 渲染回图片，再跑一次同样的 OCR，
与源图 OCR 结果做**字符多重集**比对。100 张真实稿实测：召回中位 98.2%、准确 99.0%。

**画面破坏度必须和文字质量分开量**：切成「文字区 / 非文字区」，非文字区差异应接近 0
（实测中位 1.30/255）。混在一起量会被文字区的正常差异淹没。

**四个被证伪的「自动识别转得不好的公式」判据**（别再走一遍）：
基线几何、OCR 置信度、墨迹密度、行分布匹配度，全部与正常文字重叠。
置信度最反直觉——0.80~0.99 区间读对率 83%/69%/55%/57%/58%，几乎不相关。
成立的只有「希腊字母 / ∑∏∫√ / 上下标」字符判据 + 沿同行传播。

**测试集必须贴着真实用法长**：原来 40 张以国际会议稿和欧语版式为主（行距宽松），
换成 100 张密集中文技术稿后，「行距紧时文字重叠」立刻现形（影响 24/100 张）。

## 发布链路（要用户点头才跑）

- 打包：`uv run pyinstaller pptx-finder.spec --noconfirm` → zip → `gh release create`
- 版本号同时改 `src/pptx_finder/__init__.py` 与 `pyproject.toml`（并行开发下改由合并脚本自动抬）
- **打包后必跑的两个自检**（GUI 里点不出退出码）：
  - `"PPT Doctor.exe" --selftest .selftest/set <report.json>`
    ——用 `.selftest/set`，别用 `loop_set`（后者没有 docx/pdf fixture，会假失败 10/12）
  - `"PPT Doctor.exe" --imgtext <图片> <输出.pptx>`
- **识别组件（80.7 MB）有两个源**：主源是自建更新源 `/pptutor/ocr/`（要 `ECS_PWD`，
  必须用户点头才传）；主源取不到清单时回落到 GitHub Release `ocr-v1.0.0` 这个独立 tag。
